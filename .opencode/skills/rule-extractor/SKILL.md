# 测试用例分析规则提炼

从若干测试用例中提炼共性结构，生成分析规则文件，供 test-case-completer skill 使用。

## 输入

某专题的若干测试用例（Python测试脚本框架），需包含 `@TestcaseName` 字段。

## 输出

一份分析规则 Markdown 文件，结构参考 `references/分析规则模板.md`。

## 工作流程

### 阶段一：收集用例

1. 询问用户提供测试用例（建议 3-5 个，最少 1 个）
   - 少于 3 个时，生成的规则可能不完整，需在输出中标注"初版，待补充"
   - 用户后续补充用例后可迭代更新规则
2. 确认用例属于同一专题
3. 提取所有用例的 `@TestcaseName`，列出摘要
4. 从每个用例名称中提取已有信息：
   - 类型标识（【xxx】）
   - 测试对象（什么参数/功能）
   - 测试条件（什么条件下）
   - 预期方向（正向/负向）
   - 标记名称中的模糊词（如"xx"、"某"、"适当"）
5. 检查注释字段的填写状态：
   - **空字段** → 标记为完全缺失
   - **部分填写** → 标记为信息不完整（保留已有内容，只补充缺失部分）
   - **完全填写** → 标记为已完成，作为参考基准

### 阶段二：归纳共性

逐个分析用例，归纳：

1. **用例名称模式** — 命名有什么规律？模糊词有哪些？
2. **前置条件的共性** — 环境准备有什么共同要求？是否涉及多个对象？
3. **测试步骤的差异** — 步骤之间有什么差异和共性？正向/负向的差异？
4. **预期结果的判定方式** — 成功/失败怎么判断？有无错误码？
5. **后置条件的清理方式** — 测试后怎么恢复？是否有多个清理对象？
6. **子分类** — 用例之间的差异能归纳出哪些子类型？
   - 如果子分类差异大（如开启 vs 切换 vs 共存），按子分类分别归纳检查项
   - 检查维度可以按子分类拆分，每个子分类有各自的特有检查项

### 阶段三：识别缺失模式

对每个用例检查：
- 哪些信息经常被省略？
- 哪些描述是模糊的（如"适当值"、"配置成功"）？
- 哪些步骤之间有逻辑跳跃？
- 哪些用例缺少配对的正向/负向场景？

归纳出这个专题的**典型缺失项**。

### 阶段四：生成分析规则

基于归纳结果，生成分析规则文件。**每个检查维度必须有对应的提问模板。**

1. **核心前提** — 这个专题的测试原理
2. **分类体系** — 用例的子分类
3. **用例名称解析模式** — 命名规律和模糊词
4. **检查维度** — 按前置条件/步骤/结果/后置条件列出检查项
   - 通用检查项：从模板继承（环境、对象、操作方式、判定标准、清理）
   - **专题特有检查项**：根据用例归纳补充（如计数器的"查询时机"、"计数值范围"）
5. **提问模板** — 检查维度的每个检查项必须有对应的带选项提问
   - 通用提问：从模板继承
   - **专题特有提问**：为专题特有检查项设计带选项的提问
6. **提问顺序** — 按优先级排列提问顺序：
   - 先问"测什么"（核心对象/参数），再问"怎么测"（环境/步骤），最后问"判定和清理"
   - 专题特有维度优先于通用维度（如先问计数器名称，再问小区配置）

生成后输出给用户确认，用户确认后保存为文件。

保存路径：`test-case-completer/references/{专题名}用例分析规则.md`
命名规则：与 `@TestcaseName` 中的 `【类型标识】` 对应

同时更新 `test-case-completer/SKILL.md` 中的类型映射表，将新类型指向新的规则文件。

## 输出格式

参考 `references/分析规则模板.md`。

## 规则

- 不写实现代码——只分析和生成规则
- 生成的规则文件保存到 test-case-completer/references/ 下
- 模板结构参考 `references/分析规则模板.md`
- **检查维度和提问模板必须一一对应**：每个检查项至少有一个对应的提问
- **与 test-case-completer 工作流程兼容**：生成的规则文件必须包含检查维度和提问模板两部分，供 test-case-completer 阶段二直接使用
