# 测试用例完备性补全

解析Python测试脚本框架中的用例注释，识别隐藏/缺失信息，通过对话逐个澄清后输出完整的注释块。

## 输入

Python测试脚本框架，类注释中包含用例信息：

```python
class Test_TC_000001(BaseContext):
    """
    @TestcaseNumber: TC_000001
    @TestcaseName: 【参数约束】5G_OCL_00001：xx小区不能打开ca开关
    @PreCondition:
    @TestStep:
    @TestResult:
    @PostCondition:
    """
```

## 输出

补全所有字段后的完整注释块。

## 工作流程

### 阶段一：理解用例

1. 提取 `@TestcaseName`，从 `【类型】` 标签识别用例类型
2. 逐字段检查：
   - **空字段** → 标记为缺失
   - **模糊描述** → 标记为待澄清（如"xx小区"、"适当值"、"配置成功"）
   - **步骤跳跃** → 测试步骤为空或步骤之间有逻辑断裂
3. 加载对应分析规则（references/下）：
   - `references/参数约束用例分析规则.md` — 参数约束类用例
   - `references/特性测试用例分析规则.md` — 其他类型（预留）
4. 向用户简要说明用例的已知信息和待澄清项概览

### 阶段二：逐项澄清

**核心原则：一次一个问题，给选项让用户快速选择。**

1. 按优先级顺序：前置条件 → 测试步骤 → 预期结果 → 后置条件
2. 每轮只提**一个问题**
3. **必须提供选项**（A/B/C 或勾选项），让用户选择而不是自己组织语言
4. 基于用户的回答推导下一个问题
5. 当发现新约束或信息时，可以回退到前面的阶段重新确认
6. 所有关键信息齐备后 → 进入阶段三

**选项设计原则：**
- 覆盖最常见的场景作为选项
- 留一个"其他"选项让用户补充
- 选项要具体，不要抽象

### 阶段三：一次性呈现

1. 将所有澄清后的信息填充到标准字段
2. **一次性输出完整注释块**，不要分段确认
3. 最后问一句："需要调整的地方吗？"
4. 用户反馈后修改，直到确认

## 输出格式

```
    """
    @TestcaseNumber: TC_000001
    @TestcaseName: 【参数约束】5G_OCL_00001：xx小区不能打开ca开关
    @PreCondition:
        1. 创建 FDD N1 频段、30M 带宽、SA 模式的普通小区

    @TestStep:
        1. 通过 MML 命令设置该小区的 NRCell.CASwitch 为打开

    @TestResult:
        执行 MML 命令时即被拒绝，返回错误码 800000000

    @PostCondition:
        删除创建的小区

    """
```

## 规则

- 不写实现代码——只分析和补全注释
- 用例类型识别：从 `@TestcaseName` 中解析 `【类型】`
- 每种支持的类型在 `references/` 下有独立的分析规则文件
- 新增类型：在 `references/` 下添加文件，结构参考参数约束用例分析规则.md
